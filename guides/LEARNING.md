# Recreating Klightten, one layer at a time

[Back to README](../README.md)

The goal is to understand the site well enough to rebuild it—not just keep a finished folder. Read the files in this order.

## 1. HTML: the page structure

Start with `docs/index.html`. Find its header, navigation, main sections, footer, and project dialog. Then compare `work.html` and `about.html`.

These are separate documents, not routes generated by a framework. Their navigation and footer are intentionally repeated so the complete page is visible in each file. When changing shared navigation, update all three pages.

**Exercise:** recreate the header and one project card using only HTML. Make every link and button understandable without styling.

## 2. CSS: theme and layout

Read `docs/assets/css/theme.css` before `portfolio.css`.

The theme file defines color variables, text, buttons, inputs, focus styles, dialogs, and reduced motion. The layout file describes the hero, grids, filters, cards, About page, and responsive breakpoints. The admin has its own layout file in `admin/assets/css/admin.css`.

**Exercise:** change `--accent` in one theme. Then make a three-column grid collapse into one column on a narrow screen. Keep keyboard focus visible.

## 3. JSON: content without layout

Open `docs/assets/data/portfolio.json` and read [CONTENT.md](CONTENT.md). A project is data: its title, description, status, technologies, and URLs. It does not contain HTML.

**Exercise:** add a project by hand, check JSON commas and quotes, then reload the local Work page. This should not require changing rendering code.

## 4. JavaScript: data to visible pages

| Module         | What to follow                                                         |
| -------------- | ---------------------------------------------------------------------- |
| `model.js`     | Normalization, legacy imports, public-only exports, version comparison |
| `ui.js`        | Safe DOM helpers, theme switching, project cards and dialogs           |
| `portfolio.js` | Fetch content, fill profile fields, render/filter/paginate projects    |

Follow one project from JSON to `normalize()`, then `projectCard()`, then the dialog opened by its button. Notice that imported strings use `textContent`; they are not inserted as executable HTML.

**Exercise:** recreate search with `filter()` and one input listener. Add pagination only after search works. Test the empty result state.

## 5. Admin: state and intentional saving

Read `admin/assets/js/admin.js` by function. `data` is the working draft. `persist()` normalizes and saves it locally. Forms update the draft, not the published website.

The six sections separate frequent editing from connection and backup settings. Saving a project and publishing a site are intentionally different actions. Preview includes public projects; backup includes all workspace projects.

**Exercise:** build a one-project form that writes a local draft and restores it after refresh. Add validation and a backup button before adding more features.

## 6. GitHub: a commit is not a deployment

`admin/config.js` fixes the repository destination. `admin/assets/js/github.js` handles authentication and the Contents API. It reads the existing file SHA, checks for conflicts, and sends a conditional update.

GitHub then deploys the configured `docs/` folder through Pages. The browser editor cannot modify local files or guarantee that deployment succeeded.

**Exercise:** first publish a JSON change using normal Git. Understand the diff, commit, push, and Pages result before trying the browser publisher.

## Design decisions to question as I learn

- Would another page make the content easier to understand, or only add navigation?
- Can a new field be expressed in JSON instead of hardcoded markup?
- Does a setting belong in Appearance, content editing, or publishing?
- Is the claimed security boundary real, or only hidden UI?
- Can I recover my draft if the browser is cleared?
- Does the page still work with a keyboard, narrow viewport, long title, and missing image?

The next version should grow from answers to these questions, not from adding dependencies by default.
